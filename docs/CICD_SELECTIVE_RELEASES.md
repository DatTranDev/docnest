# Automatic rolling releases

The owner superseded the multi-workflow maintenance/routine procedure with one release button. Open **Actions → Build & deploy → Run workflow → main → Run workflow**. There are no manual inputs. [One-time setup](GKE_ONE_CLICK.md) retains the existing protected `cloud-gke` environment and identities.

## Active paths

- `ci.yml`: push/PR and reusable build-only verification. The stable required check is `application`.
- `gke-build-deploy.yml`: the only manual release workflow; serializes discovery, build and rollout with `cloud-gke-deployment`, cancellation disabled.
- `cloud-images.yml`: reusable internal build/scan/publish implementation; no standalone dispatch button.

Removed the maintenance/deploy-digests/selective dispatch variants, separate scheduled-acceptance wrapper, quiescing GKE backup helper/identity setup/RBAC and obsolete VM deployment executables. Six application Deployments plus MySQL/Kafka/Redis remain required workloads. Migration Job templates are used on demand, not additional application Deployments. Historical VM infrastructure/backup references are retained for existing data/cutover inspection; they are not an active deploy path. No cloud resource or GitHub environment is deleted by repository cleanup.

## Automatic baseline and impact

`deployment_state.py` paginates repository Actions runs and artifacts, accepts only known release workflow paths, `workflow_dispatch`, main, successful completed runs and `rolloutStatus: PASS` evidence with a matching commit. It ignores PR/foreign workflow evidence and the current run. Interrupted mutations block subsequent releases; failures known to precede mutation can be retried. API/archive errors fail instead of silently selecting an untrusted baseline. Downloads and decompressed state size are bounded; signed storage redirects strip Authorization, and transport exceptions do not print signed URLs.

The full V2 environment state validates six immutable registry references, per-image source commit/run and matching scan gates. Its commit must be an ancestor of requested main. Live images must equal baseline images, all desired positive replicas must be ready/stable, and no previous Pods may still be draining. Missing/expired baseline means a full six-image same-run scanned release replaces the healthy existing apps sequentially; live old digests are rollback evidence only, never invented scan provenance.

Git diff handles merge-base, renames/deletions, shared inputs and immutable migrations. A Document source change builds Document; shared Maven changes build all dependent backends; frontend builds Web; app manifests can select rollout without building. Unknown/shared tooling conservatively rebuilds all six. The required `application` check aggregates selected Java packaging and frontend production/static builds. Browser, Testcontainers, service integration and full-acceptance jobs are removed; no test stack or synthetic login budget is created. Same-commit no-image releases may reuse a successful `build-only-v1` profile for at most24h. Build-only evidence explicitly records tests as `NOT_RUN` and cannot claim historical full acceptance. CD compiles the selected services inside their Docker builds once, including the production and standalone Web builds; it does not first invoke the reusable CI build. Push/PR CI remains independent. Backend images share one scoped Maven reactor and BuildKit layers. Every selected local image ID must match its scan before any registry push starts. Up to three images publish concurrently; the digest manifest is written only after every push succeeds. Timing-log updates use a lock so concurrent commands cannot overwrite each other. No measured CI speedup is inferred from caching configuration.

Design documentation, including `docs/04_EDITOR_ENGINE.md`, follows the documentation-only impact rule: prose edits alone neither select images nor require coordinated rollout. Contract files under `docs/contracts/` and shared Java codec/contract sources still select all six images and trigger the protocol/native compatibility gate, including when changed alongside documentation or UI. Moving or deleting those contract files retains their original-path impact. Documentation never exempts accompanying runtime, schema or contract changes from their own release checks.

Config-only changes are discovered at deploy time: effective per-service config hashes and Pod annotations select all changed consumers automatically, and trusted-proxy changes select Web. Google client changes force a Web rebuild. All six desired templates can be rendered for comparison, but only selected Deployment resources are applied. A no-op release records current approved state without restarting apps.

## Compatibility and migrations

`infra/k8s/rolling-migrations.json` pins reviewed expand-compatible migration resource hashes, normalized for checkout newlines. Every service resource must match its canonical `backend/schema/<owner>` copy. Existing migration edits/deletions are rejected by Git impact. New SQL requires a versioned hash-bound review in the same protected PR; the deployment button has no compatibility checkbox. Hash review is an approval record, not an SQL lock analyzer or proof of mixed-version correctness. Review MySQL lock/algorithm behavior and exercise real old/new readers before approving new SQL.

On first baseline adoption, owning migration Jobs run Flyway's pending history using the reviewed current set. Subsequent releases run only changed owners. Jobs use unique run/attempt names and migration-only images, never delete another run's Job, and an active migration prevents overlap. Flyway stays disabled in normal service startup. Protocol/native/event changes conservatively fail before publication unless they match the exact hash-bound expansion in `infra/k8s/rolling-contracts.json`; there is no maintenance fallback. Image rollback does not reverse SQL or external side effects.

The reviewed expansion from deployed baseline `2bb5aae` adds Identity and Collaboration routes and presence data. The old OpenAPI paths, methods, component schemas, request bodies and response shapes remain unchanged. In particular, public registration/session/`/auth/me` responses retain the three-field `User` shape; the new Web reads avatar metadata through the new profile route after authentication. Existing collaboration HTTP endpoints and their Yjs payloads remain unchanged. Identity V5 and Collaboration V3 are expand-only migrations pinned in `rolling-migrations.json`. The workflow runs those migrations before updating backends, then rolls backends before Web. Old Web clients ignore the new routes and continue using the existing HTTP collaboration path; new Web keeps HTTP polling when socket notifications are unavailable. The hash-bound review accepts only these three contract files at their reviewed bytes from that exact baseline and rejects common codec/contract changes or another baseline. This is a source and mixed-version design review, not measured cloud interoperability or functional acceptance; the build-only release profile still applies.

The 2026-10-23 security remediation changed the reviewed bytes of `openapi.yaml` and `collaboration.md` relative to the last successful deployment, `2844dd9`. The OpenAPI edits add descriptions of registration closure, verified-email sharing and their existing error responses; they do not add or remove paths, request fields, response fields or event/native payloads. The collaboration edit specifies that a presence heartbeat cannot update another user's session; its route and payload are unchanged. Existing clients can receive `REGISTRATION_CLOSED` or `EMAIL_NOT_VERIFIED` where the new security policy denies account creation or a share, and should show the error and allow retry after the account is eligible. Backend-first rollout preserves old HTTP and native readers while the new Web is published last. The two changed contract files have before and after hashes in `rolling-contracts.json` bound to baseline `2844dd9`; the unchanged `collaboration.openapi.yaml` is excluded. No other contract or shared codec file is accepted. This review does not establish live mixed-version behavior.

## Rollout and evidence

Every selected resource must pass server dry-run before ConfigMap/Job/Deployment mutation. Existing desired replica counts are preserved. Independent database-owner migration Jobs run in batches of at most two; every required migration must finish before any application update. Backends roll sequentially before Web with `maxSurge: 1`, `maxUnavailable: 0`, minReadySeconds10, backend preStop10/grace160 and Web preStop210/grace360. Startup probes use3s/100 failures (300s budget), readiness3s/10 failures (30s unhealthy window) and minReadySeconds10; liveness and shutdown/drain budgets remain unchanged. The gateway drains bounded requests up to its configured deadline. Existing cluster capacity must accommodate surge and terminating Pods; no replicas/nodes are provisioned by CI. The existing GKE BackendConfig must match the reviewed130s request/150s drain budget before mutation. It is read, never applied by the app workflow; the60s detach allowance needs measured staging acceptance.

EndpointSlices for all six apps and public HTTPS health are sampled throughout rollout. Old Pods must finish draining before success. Unselected Deployment/template/Pod identities must stay unchanged. Synthetic save/export/ACL and slow-download traffic are no longer release gates. Availability evidence covers endpoint/readiness observations only; functional behavior remains unverified by a build-only release. Single-node MySQL/Kafka remain shared failure domains.

`deployment-evidence` contains bounded before/after identifiers, previous/new image/provenance state, stage results/durations and readiness samples. It excludes arbitrary Pod environment values, credentials, migration output and document data. State remains `PENDING` after interrupted mutation and becomes `PASS` only after rollout and observer completion. Artifact retention is 90 days. Do not approve failed state or delete evidence to bypass recovery checks.

## Recovery outside deployment

The release workflow no longer creates or requires a quiesced backup. Backup identities, object storage writes, JWT access and Pod exec are absent from deploy. Existing encrypted recovery objects/keys must be preserved. Independent online snapshot/binlog capture, encrypted archival, existing-runner schedules and isolated recovery tooling are implemented in [RELEASE_RESILIENCE.md](RELEASE_RESILIENCE.md). The scripts preserve five SQL owners, generation references and numeric JWT version; actual GCS/PITR/provider recovery and measured production RPO/RTO remain PENDING. No backup infrastructure is provisioned by local commands.

After an interrupted mutation, inspect bounded stage evidence, actual Deployments and Flyway history. Recover only compatible desired application state under the environment lock, then reconcile a new audited full V2 state. Never automatically scale old apps, roll back schema or retry unreviewed migrations. Live cloud acceptance, restore and numerical availability results remain in [PROJECT_STATUS.md](PROJECT_STATUS.md).

Image-only incident recovery uses hash-bound plans, live Flyway verification, DDL fencing and a temporarily frozen deployment workflow. The protected `GKE_RECOVERY_STATE` override reconciles only the exact interrupted mutation after approved traffic checks. See [the operator procedure](RELEASE_RESILIENCE.md#interrupted-release-and-approved-image-recovery).
