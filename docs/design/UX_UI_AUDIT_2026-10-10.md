# docsnest: UX/UI audit and redesign proposal

**Review date:** 10 October 2026 · **Audience:** ages 18–25 · **Scope:** current frontend working tree and available local UI.

**Recommendation:** make the first useful action obvious, put writing above interface controls, and explain where each draft is saved. Preserve the existing editor and save guarantees while simplifying the surrounding interface.

This is a design and business-analysis deliverable, not an implemented redesign. No production application code was changed. Conversion improvements below are hypotheses to test, not measured results.

**Full visual follow-up:** [Browse all 15 screen/state design boards](ALL_SCREENS_DESIGN_GALLERY.md), including authentication, file management, source/local tools, sharing, recovery, downloads, settings and public viewing.

## 1. Current State Assessment (UX/UI Audit)

### 1.1 Review method and confidence

Reviewed the README, AI agent guide, current project checkpoint, product specification, ADR019, editor/save/share/processing specifications, collaboration and billing contracts, relevant OpenAPI fields, document schema, frontend components, styles and both language catalogs. Later accepted extensions take precedence over the original MVP exclusions: DOCX import, tables, source files and collaboration exist now.

The local app was already running on port 8080; no server restart was necessary. Inspected the introduction and local editors in the in-app browser, plus anonymous sign-in/registration. Used 1440 × 1000 and 390 × 844 viewports. English and the browser-selected dark appearance were visible during the main inspection. Did not change account preferences.

### 1.2 Business interpretation

The requested growth goal is broader than the repository's original small-group learning product. Optimize **activation first**: a person successfully writes, keeps and reopens something valuable. Treat paid conversion as a separate decision. The current billing contract explicitly keeps existing features on Free and leaves plan-specific benefits undecided.

Use three task-based audience hypotheses rather than assuming all Gen Z users have the same preferences:

| Likely job                         | Success means                                                  | Design implication                                                           |
| ---------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Write coursework or personal notes | Start quickly, retain work, produce an acceptable file         | Default to a normal document, explain saving, surface common downloads       |
| Work on a group assignment         | Give the right person access and understand concurrent editing | Separate access from collaboration; make roles and room joining clear        |
| Edit Markdown, code or JSON        | Preserve source exactly and retrieve the intended output       | Keep specialist tools easy to find without making everyone choose them first |

Validate these segments with actual 18–25-year-old users. Fast task completion, readable mobile layouts and calm feedback are design goals; slang, gamification and novelty are not requirements.

### 1.3 What already works

- The no-account editor offers immediate utility and explicitly avoids content uploads.
- Grid/list views, scoped search, previews, breadcrumbs and item menus already support file discovery.
- Rich formatting, source editing, retained mode history, Word interchange and version copies support substantive work.
- The cloud save model preserves snapshot identity, pauses conflicts and provides draft recovery. Keep those semantics intact.
- English/Vietnamese, light/dark/system appearance and keyboard-aware menu components are useful foundations.
- The white document surface in dark mode is intentional: stored text colors and print meaning should remain stable.

### 1.5 Important distinctions

Cloud autosave already exists; do not sell “add autosave” as the redesign. The existing handler uses a save queue and snapshot identity. A pending/uncertain commit must not become “Saved.” Collaboration synchronization is also distinct from a committed document version.

The product already has responsive styles; A02 concerns their effectiveness. The library already has search and filters; A11 concerns the promises users infer from their scope. “Pro has no agreed exclusive benefits” does not mean its payment orchestration is absent.

## 2. Restructuring & Flow Optimization (User Flow & Information Architecture)

### 2.1 Proposed information architecture

Keep the two persistence contexts visibly separate, with consistent editing controls:

```text
Product introduction
  Start writing without an account → Local editor (Document default)
    Document | Markdown | Code | JSON
    Open file · Download · Print / Save PDF
  Save and share with an account → Sign in / Create account
    My files
      New document · Import file · More file types · New folder
      Current-folder search · Type filter · Grid / List
      Editor → Share / Edit together · Version history · Downloads
    Shared with me
    Trash
    Account → Settings · Plan and billing · Sign out
Public document link → Read-only viewer
```

Initially keep `/intro`, `/local`, `/` and `/s/[token]` intact. Use clearer links and entry intent before changing routing. A later dedicated workspace/document URL is an option for deep links and browser Back; it requires navigation and draft-preservation design, not just moving files into a new route.

### 2.2 First-time visitor → first useful draft

1. The introduction headline names the value: “Write, keep and share your work.” Supporting text explains that writing can start without an account, while account storage enables sharing/history.
2. Primary **Start writing** opens `/local?mode=document`. Secondary **Open a file** opens a picker from a clear local entry; Markdown/Code/JSON remain direct choices for users who need them.
3. Focus the writing area. Show “This tab only · Download to keep your work” beside the title. Offer a blank document; a clearly labeled example is optional.
4. The first meaningful success is an edit plus an explicit download. Label the native format “docsnest (.tedoc) — keeps formatting”; offer Word/TXT/HTML and browser Print / Save PDF with accurate limits.
5. Place a quiet **Save and share with an account** link near the save-location explanation. Do not interrupt typing with a sign-up modal.
6. **Current-contract bridge:** download the draft, sign in in the application, then import it explicitly. Preserve the local tab until the user finishes. No authenticated API requests or content uploads originate from local tools.

A seamless “save this local draft to my account” transfer would be a later product/security design requiring explicit import consent and a compliant handoff. It is not an existing capability and is not assumed in this proposal.

### 2.3 New account → first cloud document

1. Explain the account benefit: “Keep your files, share access and return to earlier versions.” Keep the three current required fields: display name, email and password. Label display name “Name people see”; show the password rule before submission.
2. After successful registration and sign-in, show the file library with **New document** and **Import file** directly in the empty state. No separate onboarding wizard is needed.
3. **New document** opens a localized “Untitled document.” Place focus in the editor, with rename available in the title; creation can use the existing title-bearing API.
4. Show an unsaved/pending state during editing and only show **Saved to your account** after the current content token matches a successful commit.
5. Let users return to My files and reopen. Treat successful reopen as stronger activation evidence than an empty document record.

Current first-write path from an empty library: **New → choose Document → name prompt → confirm → write**. Proposed path: **New document → write**. This removes menu selection and pre-writing naming; it is an interaction-count comparison, not a timed usability result. Apply quotas and existing optimistic metadata revisions when renaming.

### 2.4 Returning user → find and resume

1. Open My files with the existing remembered grid/list preference. Keep the creation action stable.
2. Label search with current scope, for example “Search names in Class notes.” Show a visible breadcrumb and clear filters control.
3. Separate true-empty, filtered-empty, loading and failed states. If only some results are loaded, explain that before saying no matches exist.
4. Open with one click and preserve the library context for Back to files. Avoid showing the large library search while writing; Find belongs to the document toolbar.
5. Offer Recently opened later only if its source is explicitly defined. A browser-local history must say “On this browser”; account-wide recent activity needs a reliable query. Do not infer recency from currently loaded name-sorted items.

### 2.5 Share → optionally edit together

1. Owner opens **Share**. Show two separated sections: **People with access** and **Anyone with the link**.
2. Under the email field, explain “Use the email of an existing docsnest account. No invitation email is sent.” Default to **Can view**; **Can edit** has a short capability description.
3. Apply access, show inline success and the updated recipient row. Do not imply the recipient was emailed.
4. Public link creation remains explicitly opt-in and read-only. Show the seven-day expiry, Copy link, copied feedback and Turn off link. Do not automatically create a link on opening Share.
5. Place **Edit together** adjacent to sharing, with “Everyone must open this document and join editing together.” Save/check current content and confirm room join state using the existing protocol; permission to edit does not itself join a room.
6. Viewers/editors receive a role-aware access summary rather than owner controls. Never imply public links permit editing or that a recipient can rename/move the owner's file.

For small collaborative files, merge the entry points visually while preserving explicit join semantics. Disable unsupported collaboration with a reason before attempting the action; normal large-file editing remains available.

### 2.6 Download/export, import and recovery

**Cloud export:** Download → choose format → save if necessary → confirm a valid committed version → show “Preparing PDF…” in a visible download tray → Download PDF. Keep failed/cancelled states and retry guidance. If edits continue during export, label the result's version rather than implying it contains later edits. The existing export hook already attempts a save; the proposal reorganizes feedback and removes duplicate format choices.

**Local output:** Download uses the browser only. “Print / Save PDF” opens the browser print dialog; do not label it as the server's PDF exporter. Preserve supported DOCX limits and do not promise exact Word page layout.

**Import:** select a file → validate → show a filename/format summary → open as a new document by default. Importing into an existing document must explicitly say it replaces contents and preserve the current draft before switching. Rich imports should suggest the original basename; current rich-file import can fall back to a generic copy title. On rejection, state that the current document is unchanged and offer supported alternatives.

**Conflict:** stop cloud saving → explain a newer version exists → recommend **Save my changes as a copy** → offer **Download my draft** and **Open latest version** with clear consequences → let **Keep working here** retain the conflict and local changes. Never silently rebase a stale snapshot.

**JSON:** edit source → Format/Minify creates a result → edit/copy/download result independently → **Replace source with result** explicitly applies it → cloud Save now includes it. Add result provenance: “Generated from an earlier source” after source changes. Undo replacement must restore source. Empty/invalid result should never look verified solely because the source passed validation.

### 2.8 Prioritization, dependencies and measurement

**First increment:** fix mobile density, dark contrast, proactive password guidance, modal behavior, in-dialog sharing feedback, empty-state creation and JSON replacement. These address observable friction without changing backend business rules.

**Second increment:** standardize editor chrome, creation/rename, download progress, role-aware sharing, error-vs-empty states, restore guidance and bilingual terminology. Reuse existing APIs and feature public interfaces.

**Later, after product decisions:** durable deep links, account-wide recents, consistent server-side sort/type filtering across pagination, explicit local-to-account transfer, and a differentiated paid offer. `updatedAt` already exists in the Document OpenAPI schema but is omitted from the current frontend `DocumentInfo` type; a date column may be frontend integration work. An account-wide “Recently edited” order still needs verified endpoint ordering/cursor semantics—the current DAO orders the list by creation time and ID.

| Outcome                | Proposed measure                                                                                                       | Interpretation / guardrail                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local activation       | Edited local sessions that initiate a download ÷ sessions with an edit                                                 | Browser download initiation is not proof a person retained/reopened the file. Keep local events in a local research harness; do not add network telemetry to local tools. |
| Cloud activation       | New accounts that commit nonempty content and reopen that document within 24 hours ÷ new accounts                      | Empty creation alone is not activation; collect only approved scalar events, never content or titles                                                                      |
| First-value friction   | Median time and action count to first edit and first retained output, by entry path                                    | Baseline is unknown; compare like tasks and device classes                                                                                                                |
| Sharing success        | Authorized grant completion ÷ valid share attempts, plus recipient task completion in research                         | Do not equate a created public link with a viewed document; never record link tokens                                                                                      |
| Findability            | Success/time to find a named file in a >50-file library                                                                | Test loaded-page filtering explicitly                                                                                                                                     |
| Trust and retention    | Successful reopen rate; confusion about save location; conflict resolution without lost work                           | A conversion gain is unacceptable if recovery/ACL behavior regresses                                                                                                      |
| Paid conversion, later | Activated eligible accounts with verified active paid entitlement ÷ activated eligible accounts offered a defined plan | Checkout click/return is not a purchase; real billing acceptance remains pending                                                                                          |

No numeric uplift is claimed. Start with 6–8 moderated participants spanning coursework, group projects and technical writing; include mobile-first participants and keyboard use. Ask them to create a draft, retain it, find a file, share with the correct role, export, recover a conflict and explain what JSON Save includes. Measure task success, time, wrong turns and a short ease rating. Use this to refine the design, not to estimate population conversion. For a later A/B test, calculate sample size from a real baseline and agreed minimum effect; low lab traffic is better suited to task-based research.

## 3. Interface Design Proposal (UI Layout)

### 3.1 Design direction and tokens

Use a **document-first desk**: the user's writing is the main visual object. Keep docsnest's blue document mark, make navigation quiet and spend visual emphasis on the current task. This fits notes, assignments and technical drafts without treating younger users as a style stereotype.

I considered a richer library dashboard with recent cards and starter templates, then removed it from the first proposal: the current product has no template system or dependable account-wide recents view. The design instead improves the existing writing and file-management tasks.

| Desk            | `#F5F7FB`                                                                                                  | App background; restrained separation from paper                                                          |
| Ink             | `#202B3A`                                                                                                  | Main text                                                                                                 |

Dark theme should use distinct background/surface/text tokens rather than inherited light-mode muted colors. Retain white document paper, test colored document text separately, and preserve reduced-motion behavior. Do not animate routine saves or reorder files while someone is targeting an action.

### 3.4 Accessibility and state acceptance criteria

- Modal opens with appropriate focus, contains Tab/Shift+Tab, closes with Escape where safe and returns focus to its trigger. Backdrop content is inert. Follow the [W3C modal pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).
- Aim for 44px touch controls in the proposed mobile UI. WCAG 2.2's AA minimum is 24 × 24 CSS px with specified exceptions, so 44px is our comfort target, not a claim about the minimum. See [target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).
- Test keyboard focus at desktop/mobile widths and zoom; sticky bars must not completely obscure it. See [focus-not-obscured guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum).
- Validate light/dark text and control contrast from computed styles, including errors, placeholders, selected tabs, tooltips and hover/focus. Do not rely on color alone.
- At 320, 390, 768 and 1440 CSS px, inspect long Vietnamese labels, long filenames and keyboard-open layout. Keep the editable caret visible. Proposed 390px canvas-start target must be measured after implementation.
- Use inline `aria-describedby` error/help relationships and polite live updates for save/export status. Avoid repeated announcements on every keystroke.
- Every disabled action needs an available explanation: permission, offline state, unsaved prerequisite or size limit. Keep zero-content, loading, error and unavailable states distinct.
- Validate owner/editor/viewer/public behavior, conflict/draft recovery, source-result replacement, retained undo and localized messages against actual services when implementing. Functional checks must not be replaced by the concept image.

## 4. UX Writing Refinement Table

### 4.1 Voice and terminology

Be friendly through clarity: describe the action, its consequence and the next step. Use sentence case, plain verbs and consistent file names. Avoid product-engineering terms in the main instruction when a common term is accurate. Retain familiar specialist language such as JSON and Markdown where it identifies an actual tool.

Use **My files** as the umbrella for rich documents and source files; use **document** for the rich editor and **file** where multiple formats are supported. **Save** means committing to the account; **Download** means initiating a browser download. **Can view / Can edit** are human-facing permissions; API enums remain unchanged. “Saved,” “Copied” and “Downloaded” require evidence appropriate to the action—browser download initiation alone cannot prove a file was retained.
