# Runtime OS finding review

Runtime images refresh package indexes and upgrade installed packages once per build run. The same refresh identifier is shared across the five Java builds so the patched base layer remains reusable within that run. Web refreshes its Alpine runtime packages separately. The publication gate still rejects every High or Critical finding; there are no severity exclusions or new ignore rules.

The October 17 local scan after upgrading the runtime packages found 53 Medium and four Low package findings in each Java image, representing 46 distinct CVEs across both severities. None had a fixed version in that scan database. Web had zero OS findings. These are local image results, not a production scan or an approval to accept risk. Exact image IDs, database metadata, package versions, CVE identifiers and vendor references remain in the generated `image-os-scan.json` and `image-os/*-trivy.json` evidence. Execution and cloud gate status belong in [PROJECT_STATUS.md](PROJECT_STATUS.md).

The upgrade removed the previously detected fixable curl/libcurl High finding and the fixable freetype/libpng Medium findings. Remaining findings include 20 rust-coreutils and eight PCRE2 package findings, five GnuTLS findings, and findings in shell, C runtime, compression, XML, identity and system libraries. A duplicated CVE in multiple installed binary packages counts more than once in package totals.

Do not dismiss these findings simply because the application is Java. Backend processes handle untrusted HTTP and file data, use native JVM/runtime libraries and invoke bounded external tooling for health checks. The application containers run as nonroot, private services are behind the gateway, and secrets are excluded from image layers. Those controls reduce some attack paths but do not prove individual CVEs unreachable. GnuTLS/PCRE2/XML findings require reviewing the affected native caller and input path; command-line utilities require checking whether application-controlled arguments or file names can reach them.

For every release, retain the exact image scan alongside immutable build provenance. When a vendor fixed version becomes available, rebuild with a fresh package-refresh identifier, scan the resulting image IDs and run the relevant application checks before publication. Changes to the base distribution, JVM or removal of installed packages require a separate compatibility check; do not remove packages blindly to reduce a counter. Any proposed exception needs an identified CVE, affected version, demonstrated reachability analysis, owner, expiry and remediation condition. This document grants no exception and does not replace the High/Critical gate.
